# P0-5 システム移行ウィザード — 詳細設計

> 状態: 設計（未実装）｜依存: P0-3/4（バックアップ・復元）、P0-6（step-up）、共通基盤（読み取り専用モード）

## 1. 目的
運営主体・担当事業者・クラウド基盤が変わっても、**手順と検証結果が画面に残る形で**移行できるようにする。移行は「データの移送」と「基盤（Git・Vercel・Redis・ドメイン）の付け替え」に分かれる。前者はウィザードで扱い、後者は画面上のチェックリストと手順書（`docs/MIGRATION_RUNBOOK.md`）で扱う。

## 2. 移行の単位

| 対象 | 移行方法 | ウィザードでの扱い |
|---|---|---|
| ソースコード・Git 上のデータ（events.json・アーカイブ・拠点） | GitHub リポジトリの移管、または fork/clone | チェックリスト（コミットSHAの一致を自動確認） |
| Redis のデータ（手動イベント・上書き・アカウント・異動記録） | バックアップ → 復元（P0-3/4） | **自動**（§4） |
| 環境変数・Secrets | 移行先で**新規に発行**する（値は移送しない） | 名前・設定有無のみ確認（値は表示しない） |
| ドメイン・DNS | レジストラ・DNS の操作 | チェックリスト＋疎通確認 |
| 外部サービス（OCR/LLM・ntfy・Open-Meteo・国土地理院） | 移行先で契約・キーを発行 | チェックリスト |

## 3. 環境診断（`api/admin/system.js` `op=diagnose`）
移行元・移行先の両方で実行し、結果を JSON で保存できるようにする。

- アプリ: `appVersion`、`schemaVersion`、デプロイのコミットSHA（`VERCEL_GIT_COMMIT_SHA`）
- 環境変数: 必要な変数の**名前ごとの設定有無のみ**（`shared/envSpec.cjs` に必須/任意・用途を一元定義し、DEPLOY.md の表もここから生成する）
- Redis: 接続・読み書き・レイテンシ、主要キーの件数
- 静的データ: `events.json` / `offices.json` の件数・sha256・更新日時
- 外部 API: 天気・ジオコーディングの疎通（1回だけ）
- セキュリティ設定: `LEGACY_*` フラグの状態、平文パスワードのアカウント数、MFA 未登録の管理者数

権限: `system:migrate` または `system:manage`。値そのもの（URL・トークン）は返さない。

## 4. ウィザードの流れ（管理画面「システム」→「移行」）

```text
STEP 1 移行元の診断 ………… diagnose を実行し、警告があれば一覧表示（例: 平文パスワードが残っている）
STEP 2 バックアップ ………… P0-3 の export（step-up）。sha256 を画面に控える
STEP 3 移行先の準備確認 …… 移行先で diagnose を実行した結果 JSON を読み込む
                            （移行元から移行先への直接接続は行わない。§6）
STEP 4 互換性確認 ………… schemaVersion・appVersion・必須環境変数の有無を突き合わせる
STEP 5 リハーサル ………… 移行先で P0-4 の preview を実行し、差分と件数を確認する
STEP 6 切替準備 ………… 移行元を読み取り専用モードにする（以降の編集を止める）
                            → 最終バックアップ → 移行先で apply
STEP 7 検証 ……………… 移行先で diagnose を再実行し、件数・sha256 を移行元の最終バックアップと照合する
STEP 8 切替 ……………… DNS / SITE_URL / SITE_ORIGINS の変更（チェックリスト）→ 公開トップ・詳細直リンク・管理ログインの疎通確認
STEP 9 切り戻し期間 ……… 既定14日間は移行元を読み取り専用のまま残す（切り戻し手順は §7）
```

- 各 STEP の結果（実行者・時刻・診断結果・sha256）は `migration:<id>` に保存し、監査に `system.migrate.*` として記録する。
- STEP 6 以降は step-up を必須とする。

## 5. 移行先への初回ログイン（ブートストラップ）
移行先の Redis は空のため、アカウントがまだ無い。移行先の環境変数 `ADMIN_ACCOUNTS_B64` に**緊急用 national_admin 1件**を設定してデプロイし、そのアカウントで STEP 5〜7 を実行する（P0-1 §9 の緊急用アカウントと同じ仕組み）。

## 6. 移行元と移行先を直接つながない理由
移行元から移行先の API を呼ぶ方式は操作が少なく済むが、移行元に移行先の資格情報を持たせる必要があり、URL の取り違えで別環境へデータを送る危険がある。そのため**ファイル（バックアップ・診断結果）を人が持ち運ぶ方式**を採用する。各ファイルは sha256 で取り違えを検知する。

## 7. 切り戻し
- STEP 8 の前: 移行元の読み取り専用モードを解除するだけで元に戻る。
- STEP 8 の後（切り戻し期間中）: 移行先で最終バックアップを作成 → 移行元で復元 → DNS を戻す。切り戻し期間中は、移行先での変更も失われないよう、この手順を必ず踏む。

## 8. 手順書（新規 `docs/MIGRATION_RUNBOOK.md`）の構成
1. 必要な権限・アカウント（GitHub・Vercel・Upstash・レジストラ）
2. 移行先の基盤準備（リポジトリ移管・Vercel プロジェクト作成・Upstash 作成・Secrets 設定。`envSpec` の一覧に沿う）
3. ウィザードの各 STEP と判定基準
4. 切替当日のタイムライン（読み取り専用にする時刻・利用者への告知）
5. 切り戻し手順
6. 移行完了の判定（引継ぎ書 Appendix D の該当項目）

## 9. テスト
- `envSpec.test.cjs`: コード中で参照している `process.env.*` がすべて `envSpec` に定義されていること（静的検査）。DEPLOY.md の表との一致
- `diagnose.test.cjs`: 秘密の値が応答に含まれないこと、Redis 障害時にも部分的な結果を返すこと
- `migrationCompare.test.cjs`: 互換性判定（schemaVersion の大小、必須変数の欠落）
- 手動: 検証環境同士で STEP 1〜9 を通しで1回実施する（リハーサル）

## 10. ロールバック
ウィザードは既存データを直接変更しない（変更は P0-4 の復元経由のみ）。機能の停止は権限 `system:migrate` を外すだけでよい。
