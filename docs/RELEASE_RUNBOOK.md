# リリース手順書（基盤変更の本番反映）

アカウント管理・組織マスタ・承認フローなど、**運営データや権限に関わる変更**を本番へ出すときの手順。
「実装が終わった」ことと「本番で運用できる」ことは同じではない。次の順番を1つも飛ばさない。

```text
実装 → CI → データ移行の確認 → バックアップ → Preview 検証 → 本番デプロイ → 本番スモークテスト → スクレイプ完走の確認
```

スクレイパーだけの修正（運営画面・API・データ構造を変えないもの）は、CI と手動スクレイプ1回の確認で本番へ出してよい。

## 1. CI（すべて必須）

```bash
npm ci
npm test
npm run build
node scripts/check-data-quality.mjs
npm audit --omit=dev
# スクレイパーを変えた場合
node --check scraper/index.js
node scraper/index.js --mock
```

PR の「PR Check」がすべて成功していること。ゲートを弱めて通すことはしない。

## 2. データ移行の確認

データ構造を変える PR では、移行スクリプトを **dry-run → 実行 → 再実行（冪等の確認）** の順に Preview で試す。

- 既存イベント（`manual:events`）・上書き（`manual:overrides`）・監査ログ（`manual:history`）が消えない
- 既存アカウントが意図せず無効化されない。担当 office が変わらない
- 2回実行しても重複・再生成が起きない
- 移行ログ（件数・差分）が残る

## 3. バックアップ（本番デプロイの直前）

1. 本番の運営画面に national_admin でログイン → 「システム」→「バックアップを作成」（パスワード再入力）
2. ダウンロードしたファイルを検証する:
   ```bash
   node scripts/verify-backup.mjs jsdf-backup-YYYYMMDD-HHmm.json
   ```
   件数・schemaVersion・checksum・作成日時・「秘密項目なし」を確認し、合格したものだけを保管する。
3. 保管先は運営が管理する暗号化ストレージ。**リポジトリ（公開）・チャット・メールには置かない**。

## 4. Preview 検証（`docs/PREVIEW_ENVIRONMENT.md`）

Actions →「Preview デプロイ（検証環境）」で対象ブランチをデプロイし、ブラウザで確認する。

| ロール | 確認すること |
|---|---|
| office_editor | ログイン／自事務所イベントの作成・下書き保存／担当外イベントの操作が拒否される／公開できない |
| office_manager | 自事務所イベントの編集・承認・公開・受付終了・中止・削除 |
| pco_admin | 自地本全体の閲覧・管理／他地本が拒否される |
| national_admin | 全国の閲覧・管理／アカウント管理・組織管理（該当機能の実装後）／バックアップ |
| auditor | 監査閲覧のみ／イベントを変更できない |
| system_admin | システム管理／イベント公開の権限が付いていない |

公開フローの E2E（最低1本）: office_editor が下書き作成 → office_manager が承認・公開 → 公開 API（`/api/manual-events`）に出る → 公開サイトに表示される → 編集・中止・受付終了が公開サイトに反映される → 監査履歴に残る。

## 5. 本番デプロイ

条件: CI 成功・移行確認済み・バックアップ取得と検証済み・Preview 検証済み・下記のロールバック手順を確認済み。
PR を master へマージすると `deploy.yml` が本番へデプロイする（テスト・ビルド・データ品質のゲート付き）。

## 6. 本番スモークテスト（デプロイ直後）

公開サイト表示／admin.html 表示／ログイン・ログアウト／自事務所イベントの作成・下書き・承認・公開・公開サイト反映・編集・中止／監査履歴／在席状況／報告一覧／過去イベント。
テスト用イベントは確認後に削除する。

権限（テストアカウントで）: office 担当者が他 office を変更できない／pco_admin が他地本を変更できない／auditor がイベントを変更できない／無効アカウントでログインできない／ロール・office の変更後に旧セッションが失効する。

## 7. スクレイプ完走の確認

デプロイ後、定期スクレイプを最低1回（できれば1日分）完走させる。ジョブサマリの「データ品質・差分検査」で次を前回と比べる:
イベント総数・地本別件数・手動イベント・上書き・検疫・アーカイブ。品質ゲートが停止した場合は完了扱いにしない。

## 8. ロールバック（デプロイ前に手順を確認しておく）

| 対象 | 戻し方 |
|---|---|
| コード | Vercel → Deployments → 直前の本番デプロイを「Promote to Production」（即時）。恒久対応は `git revert` の PR |
| 運営データ（Redis） | 手順3のバックアップから復元（復元機能は Phase 2。それまでは運営者と開発者で手動復元） |
| アカウント（新ストア導入後） | 環境変数 `ACCOUNT_STORE=env` で旧方式（`ADMIN_ACCOUNTS_B64`）へ戻す。旧方式は移行確認が終わるまで削除しない |
| office → officeId（組織マスタ導入後） | 旧 `office` 文字列での判定へ戻すフラグで切り替える。旧値は移行確認が終わるまで削除しない |
| 公開イベント（events.json） | 直前の正常なコミットの `public/data/events.json` を戻す PR（生成物の手編集はしない） |
| スクレイプが品質ゲートで止まる | 公開データは変わらない（コミット・デプロイがスキップされる）。原因を直すまで前回データのまま |
