# 小規模試験運用案（1募集案内所向け）

> 本案は、現場で必要性が認められた場合に検討する**小規模・短期間の試験運用**のたたき台です。
> 正式導入を前提としたものではなく、効果と現場の負担を確認することが目的です。
> 本サイトは**非公式・試作**であり、防衛省・自衛隊の公式サービスではありません。

## 目的
- 実際の業務の中で、サイトと管理機能が**役立つか・負担にならないか**を確認する。
- 一般利用者・担当者双方にとっての**効果と課題**を把握する。
- 東京地本全体への紹介・拡大を検討する**判断材料**を得る。

## 対象
- 最初は**渋谷募集案内所など1案内所のみ**。
- 登録対象は、その案内所が担当する**イベント情報**（説明会・見学・体験など）。
- 申込み受付・個人情報の取り扱いは**対象外**（従来どおり公式サイト・公式窓口）。

## 期間
- **1〜3か月程度**（開始日・終了日は現場と相談して決定）。
- 中間で1回、終了時に1回、振り返りを行う。

## 参加者
- 募集案内所の担当者**1〜2名**（うち1名は公開可否を判断する責任者）。
- 開発者**1名**（システムの保守・不具合対応・設定）。

## 役割分担（分野ごと）
| 分野 | 主担当 |
|---|---|
| イベント内容の正確性 | 募集案内所 |
| 日付・会場・締切・申込方法の確認 | 募集案内所 |
| 公開・非公開の最終判断 | 募集案内所（責任者） |
| 利用者への公式な案内 | 募集案内所の判断 |
| システムの保守・不具合修正 | 開発者 |
| 技術的なセキュリティ設定 | 開発者 |
| アカウント利用管理 | 双方で協議 |
| 障害発生時の情報共有 | 双方 |

- 「責任を半々」とはせず、上記のとおり分野ごとに整理する。正式運用時には文書化する。

## 対象イベント
- その案内所が担当する、**今後開催予定**のイベント。
- 試験中の動作確認には、**「【動作確認用・公開禁止】」と明記したテスト用イベント**を使用し、一般利用者に誤解を与えないようにする（確認後は速やかに非公開・削除）。

## 登録から公開までの流れ
1. 担当者が管理画面に**ログイン**。
2. イベントを**下書き**で入力（日付・会場・対象・締切・内容・公式リンクなど）。
3. 責任者が内容を**確認**（誤り・反映漏れがないか）。
4. 問題なければ**公開**。
5. 変更・中止が出たら**速やかに修正／非公開**。
6. すべての操作は**操作履歴**に記録される。

## OCR・スクレイピングの扱い
- 試験運用では、**担当者の直接入力を基本**とする。
- 自動収集（スクレイピング・OCR）は、**入力の補助**や**掲載漏れの検知**として併用する。
- 自動収集分は、公開前に担当者が確認する（OCRの誤認識が残り得るため）。

## 個人情報の扱い
- 本システムは**個人情報を受け付けない**。
- イベント申込み・問い合わせは、従来どおり**公式サイト・公式窓口**へ案内する。
- 管理画面に氏名等の個人情報を入力しない運用とする。

## 測定項目（効果と負担の確認）
- 登録したイベント件数／更新・修正の回数。
- 入力〜公開までにかかる**手間・時間**の体感。
- 誤公開・反映漏れ・修正の発生有無と件数。
- 一般利用者からの反応（閲覧の手応え・問い合わせ傾向など、可能な範囲で）。
- 不具合・障害の発生有無と対応状況。
- 担当者の率直な所感（続けたいか・負担か）。

## 定例確認
- 週1回程度の短い情報共有（チャット・メール・口頭いずれか）。
- 中間（開始から約半分）で振り返り、運用の調整を行う。

## 障害時の連絡
- 不具合・表示異常・ログイン不可などが起きたら、**担当者→開発者**へ連絡（連絡手段は事前に取り決め）。
- 開発者は状況・影響範囲・暫定対応を共有する。
- 重大な事象（誤公開・他案内所の情報が見える等）が疑われる場合は、**一旦該当機能の利用を止め**、原因を確認する。

## 中止条件
- 次のいずれかが起きた場合は、試験を**中止**して原因を確認する。
  - 担当範囲外（他案内所・他地本）の情報を操作できてしまう。
  - ログアウト後や無効化後も操作できてしまう。
  - 個人情報が保存・表示される。
  - 公開サイトが表示できない／イベント件数が異常に減少する。
  - 実在イベントの誤削除・誤公開が起きた。
  - 別の担当者のデータが表示される。
- 現場判断で**いつでも中止できる**ものとする。

## 終了後の評価
- 評価票（[SHIBUYA_EVALUATION_SHEET.md](SHIBUYA_EVALUATION_SHEET.md)）を用いて振り返る。
- 効果・負担・課題・必要な追加機能・費用/保守/責任分担の条件を整理する。
- テスト用イベントの削除・後片付けを確認する。

## 東京地本全体へ拡大する条件（例）
- 現場で**一定の有用性**が確認できること。
- 担当者の**負担が許容範囲**であること。
- 権限分け（案内所単位／地本単位）・操作履歴・公開承認が**実務に合う**こと。
- 費用・保守・責任分担・継続体制について**条件の合意**が得られること。
- 必要な追加機能（承認フローの強化、表示用管理番号 等）の方針が立つこと。
- 東京地本への**正式な紹介・取次ぎ**の合意が得られること。

> 拡大は段階的に行う前提とし、いきなり全案内所へ広げることは想定しない。
